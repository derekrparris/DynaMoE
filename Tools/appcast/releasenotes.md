### 📦 What's New in 26.12
* **Subagents that are real agents now:** A delegated run is no longer a canned pipeline picked by role name. It is a headless agent loop on a real model — your loaded local checkpoint or a cloud provider you have configured — with its own isolated context window, its own tool scope and loop guards, and a structured report handed back to the coordinator. `spawn_subagent` asks which backend, preset, budget, isolation and tool set the run gets, and a model-backed spawn stays an explicit Settings choice, so an omitted argument never silently sends your code to a cloud model.
* **Runs that survive the app and are inspectable:** Every run is written to disk as it goes, so closing the app no longer erases it: on relaunch you can read its transcript, steps, cost and status in the Subagents inspector, and apply or discard its work. The inspector replaces the old drawer, with inline spawn cards, notifications, and reports relayed to the coordinator at the start of its next turn.
* **Writer subagents work in their own checkout:** A run that can write gets a git worktree of its own, so it cannot edit the files you are looking at while it works. Its changes come back as a diff against the commit it branched from, and nothing lands until you approve it: the coordinator can call `apply_subagent_changes`, or you can press Apply Changes in the inspector, and both go through the same approval card. A cancelled run keeps its worktree until you clear it, so a Stop cannot throw away the only copy of its work.
* **Scheduling, budgets and cancellation:** Runs are queued by priority against real capacity (one local engine slot, a pool per cloud provider), with queue timeouts, a cancellation tree that stops only the runs the stopped turn owns, per-run and per-session cost limits, and retention settings for what is kept on disk. Settings → Agent & Tools has the backend, cloud model, cost limit, concurrency, retention and notification controls.

### 🐛 Fixes
* **Long answers rendering blank:** A 50-60k-token answer was laid out as one view and grew past the largest layer the window server can paint, so the transcript went blank until something happened to change its height. Answers are now split across several smaller rows when they would grow too tall (bounded by lines as well as characters, since a long diff is short in characters and very tall on screen), while a normal message still renders as exactly one row. Code blocks, tables and tool output inside a turn no longer each open their own scroll area, which had been multiplying that cost.
* **Reasoning traces, tool cards and plan documents blanking a row:** Those ride a single row and cannot be split, so 20-30k tokens of context in any one of them could still push the row past the paint limit. They are now drawn in a capped scroll area that keeps the content readable without growing the row, and tool argument values and errors get the same chunked, capped treatment as output instead of building an oversized row.
* **Opening a long conversation:** Every message was parsed before the window could draw, stalling it for seconds on a long history. A message too short to need its own rows is now parsed only when it scrolls into view, and conversation saves coalesce around the first change of a burst instead of restarting their timer on every change, so a streaming turn reaches disk while it runs.
* **Turbo Mode silently reverting to Safe Mode:** "Safe Mode" is only the label for a false Turbo flag, and two writers cleared it without a Turbo click: the dogfood benchmark wiped the setting instead of restoring it, and the plan handoff reverted it to its previous value whenever its send was refused, so "Code with Turbo" turned Turbo back off. Both now leave your preference alone, and every flip is announced and logged. Turbo also cannot approve away its own switch any more: a tool call that rewrites this app's preferences is never auto-approved, so the command still has to be confirmed.
* **An approval card whose Approve button did nothing:** A card could outlive the turn waiting on it, so after a Stop the button resolved nothing and the call hung. A stopped turn now resolves its approval as rejected, a decision that arrives before its waiter registers is remembered instead of lost, and a stop can no longer run the tool call it had just approved.
